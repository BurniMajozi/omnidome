## Summary

Unlike the mobile apps and much of apps/web, `services/admin` is **genuinely wired** — every endpoint hits real Postgres via parameterized SQL, with tenant scoping, RBAC helpers, audit logging, and rate limiting. No mock/stub data. So this review is about **access control and correctness**, and it surfaced a real **privilege-escalation blocker**.

Verified supporting facts before reporting:
- `services/common/db.py:147` — `get_async_session` **commits** after the handler returns. Consequence: a DB error inside the swallowed-exception audit path can poison the transaction and roll back the *main* mutation with a 500.
- `services/common/entitlements.py` — `EntitlementGuard` checks only whether the tenant has the `admin` module enabled; it does **not** check the user's role. So the per-endpoint `_require_platform_admin` / `_require_tenant_admin` calls are the **only** user-level authorization.

Severity legend: 🔴 blocker · 🟠 high · 🟡 medium · ⚪ low

## Findings

### 1. 🔴 Missing authorization on `create_role` and `create_user` → privilege escalation — **FIXED (2026-07-24)**
**File:** `services/admin/main.py` (`create_role` line ~449, `create_user` line ~880)

Every other mutating endpoint gates on `_require_platform_admin` or `_require_tenant_admin` (create_tenant, update/delete tenant, list/get/update/delete role, assign/remove role, update/deactivate user, reset-password, all commission-tier writes). **Two endpoints did not** — they called only `_auth_rate_limiter.check(request)` and went straight to the DB:

- `create_role` — any authenticated tenant user could create a role and attach **arbitrary permission keys** (including `platform.admin`, `org.admin`) pulled from the `permissions` table.
- `create_user` — any authenticated tenant user could create a user, **set its password**, and **assign any `role_id`** (with no check the role belongs to their tenant).

Chained: mint an admin-permission role → create a user with that role and a known password → log in → platform/tenant admin. Since `EntitlementGuard` only gates the *module* (not the user), any member of a tenant that has the admin module enabled could do this.

**Fix applied:** added `await _require_tenant_admin(ctx, session)` to both endpoints (matching every sibling), and added a tenant-scoped role-existence check in `create_user` before assignment (mirrors `assign_role`). Bootstrap is unaffected — the first tenant admin is created by the `provision_tenant` SQL function, not this HTTP endpoint.

---

### 2. 🟠 Tenant admins can grant platform-scoped permissions
**File:** `services/admin/main.py` — `create_role` / `update_role_permissions`

Even with finding #1 fixed, a **tenant** admin can create/update a role whose permission set includes platform-level keys (e.g. `platform.admin`), then `assign_role` (tenant-admin gated) it to a user. Nothing restricts the assignable permission keys to the tenant scope. A tenant admin should not be able to manufacture a platform admin.

**Recommended:** when the caller is not a platform admin, reject permission keys outside an allowed tenant-scope set (or filter them out) in `create_role` and `update_role_permissions`. **Decision needed** on the exact allow/deny list of permission keys.

---

### 3. 🟠 Audit-log failures are swallowed but can still abort the whole request
**File:** `services/admin/main.py` — `_log_audit` (line ~152)

`_log_audit` wraps its `INSERT` in `try/except` and only logs a warning on failure — intended as "audit is non-fatal." But because `get_async_session` commits the shared transaction after the handler, if the audit `INSERT` itself errors (e.g. the `metadata` dict isn't accepted by the JSONB column, or the row violates a constraint) the transaction enters an aborted state, the later `session.commit()` raises, and **the main mutation is rolled back with a 500** — the opposite of "non-fatal," and audit entries are silently lost either way.

Note the `metadata` bind passes a **Python dict** straight to `:metadata`; whether that's accepted depends on the driver/column type — worth verifying it's serialized (it's a plausible real failure trigger). Two separable concerns:
- **Integrity:** for a compliance audit trail, silent loss of audit rows is itself a problem.
- **Isolation:** write the audit row on a *separate* session/transaction (or savepoint) so an audit failure can't roll back business data.

**Decision needed:** treat audit as best-effort-but-isolated, or as mandatory (fail the request if it can't be recorded)?

### 4. 🟡 `provision_tenant` failure is swallowed → half-provisioned tenant
`create_tenant` (line ~275) calls `provision_tenant(...)` in a `try/except` that only warns. A provisioning failure leaves a tenant row with no seeded roles/admin/modules, and the caller gets a 201 as if it succeeded. Consider surfacing the failure (or a `provisioned: false` flag) rather than warning-and-continuing.

### 5. 🟡 Rate limiter is per-process, in-memory
`RateLimiter` (module-level instances) is per-IP but per-instance. Behind multiple replicas / a proxy the effective limit is `replicas × N`, and it depends on how client IP is derived (X-Forwarded-For). Fine for single-instance dev; note it for horizontal scaling. (Impl lives in `services/common/rate_limiter.py` — out of this file's scope.)

### 6. ⚪ `datetime.utcnow()` used throughout
Deprecated in Python 3.12+ (returns a naive datetime). Prefer `datetime.now(timezone.utc)`. Cosmetic; consistent with the rest of the codebase, so a repo-wide change, not a per-service one.

## Fixes applied (2026-07-24, in-session)

`services/admin/main.py`:
- **`create_role`**: added `await _require_tenant_admin(ctx, session)`.
- **`create_user`**: added `await _require_tenant_admin(ctx, session)`, plus a tenant-scoped role-existence check before assigning `role_id`.

## Non-issues (verified)

- **Dynamic `set_clause` SQL in `update_tenant` / `update_user` / `update_commission_tier` is NOT injectable.** The `{key}` fragments come from a fixed whitelist of payload field names, and all *values* are bound parameters. Safe.
- **`/internal/users/by-email` bypassing `get_auth_context` is by design** — it's the pre-tenant identity bootstrap, correctly gated by the internal shared secret and in `EntitlementGuard.public_paths`; it still passes through the global rate limiter.
- **`audit_log` GET authorization is sound** — cross-tenant queries require platform admin; same-tenant/no-tenant queries force `tenant_id = ctx.tenant_id` for non-platform admins.
- **No mock/stub data anywhere in the service.**
